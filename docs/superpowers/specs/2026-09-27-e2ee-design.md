# loaf native — end-to-end encryption (SDK phase 4)

Phase 4 of `docs/superpowers/plans/2026-09-26-sdk-wiring-roadmap.md`: this
device can be verified, by emoji from another device or by the recovery key;
history comes back from key backup; a fresh account can set up recovery; a
lost identity can be reset; and another of your sign-ins can ask this one "is
this you?". Encrypted rooms become readable and, once this device is
verified, writable. It amends `2026-09-20-loaf-native-design.md` ("Verifying
a session", the authority for the panel's steps and copy) only where this
document says so, and extends `2026-09-27-timeline-design.md` ("Encrypted
rooms before phase 4").

## Scope

**In:**

- Verifying this device by emoji (SAS) against another of your devices.
- Verifying with a recovery key or passphrase, including healing an identity
  that has cross-signing but no key backup, or the reverse.
- Restoring history from key backup, with a count.
- Setting up recovery on an account with no identity.
- Resetting identity, with re-authentication by password or SSO.
- The incoming "is this you?" from another of your sign-ins.
- Encrypted rooms: sending once this device is verified; locked rows
  re-mapping when keys arrive; every message action where the room is
  writable.

**Out, and when each arrives:**

| Deferred | Phase | Why |
|---|---|---|
| QR verification | later | The spec draws emoji only |
| Verifying other people | later | No UI for it in the spec |
| Resuming a bulk restore after a quit | never | Rooms fetch missing keys from backup on their own |
| Encrypting the sqlite store at rest | later | Already deferred from phase 1 |
| Creating a passphrase | never | The spec rules it out |

## Decisions

- **All five flows land.** Set up and reset are tested live only on a
  throwaway password account, `@loaf-test:loaf.moe`, which Chris creates.
  Never on Chris's account, and never on `hermes`, whose agent would lose its
  encrypted history.
- **A room is writable once this device is verified.** Sending from an
  unverified device is possible, but recent Element excludes unverified
  devices from key sharing, so replies would be unreadable here and others
  would see the message flagged. Until verified, the composer's place offers
  the way forward.
- **Trust is read from the SDK, never claimed by the panel.** The notice goes
  when device keys say this session is signed.

## The seam

`Verifier` (`lib/ui/verify/verifier.dart`) is what `VerificationController`
awaits instead of its timers. `MockVerifier` (`lib/ui/mock/`) holds today's
timer behaviour, so `LOAF_BACKEND=mock` and the existing panel tests play as
before. `MatrixVerifier` (`lib/matrix/matrix_verifier.dart`) wraps the SDK;
all SDK contact stays in `lib/matrix/`.

| Member | Meaning | Matrix |
|---|---|---|
| `otherSessions` | names of your other devices | `userDeviceKeys[me]`, minus this device and blocked ones |
| `verifyWithDevice()` | starts an outgoing request, returns a `DeviceVerification` | `userDeviceKeys[me].startVerification()`, SAS only |
| `unlock(keyOrPassphrase)` | `unlocked`, `wrongKey` or `unreachable` | `restoreCryptoIdentity`, or the in-place heal (see below) |
| `restoreHistory()` | a stream of `(restored, total)` | `getRoomKeys` once, then `loadFromResponse` room by room |
| `createIdentity({wipe, reauth})` | returns the new recovery key | `initCryptoIdentity()`, with `onUiaRequest` answered through `reauth` |

`DeviceVerification` is one handle for both directions: a `Listenable` whose
phase is `waiting`, `emoji(List<SasEmoji>)`, `waitingForOther`, `done`,
`needsKey` or `cancelled`, with `accept()`, `match()`, `mismatch()`,
`unlock(key)` and `cancel()`. The Matrix handle wraps one `KeyVerification`:

| `KeyVerificationState` | Phase |
|---|---|
| `waitingAccept`, `askChoice` | waiting |
| `askSas` | emoji (`sasEmojis`) |
| `waitingSas` | waitingForOther |
| `askSSSS` | needsKey |
| `done` | done |
| `error` | cancelled (`canceledCode` is logged, not shown) |

`VerificationController` keeps every step, guard, `canGoBack` and the done
linger it has now. Its constructor takes a `Verifier` in place of
`otherSessions` and `consumeFailure`. The mock's "fail the next connection"
lever moves into `MockVerifier`.

**Incoming.** `MatrixSession` listens to `client.onKeyVerificationRequest`,
keeps requests from your own user only, and surfaces each as
`LoafSession.incoming`. `IncomingRequest` gains its `DeviceVerification`. The
shell already pops the panel from `incoming`.

**The shell.** The "arrives in the next build" toast in
`app_shell.dart` `_openVerification` is removed; a real session opens real
panels. `markVerified` stays a no-op on `MatrixSession`.

## The routes

**Another device (emoji).**

1. The request goes out; the panel waits. Back cancels the request.
2. The other side accepts; the SDK starts SAS; the 7 emoji show.
3. "They match" calls `acceptSas()` and waits for the other side. "They don't
   match", a cancel from either side or the protocol's timeout go to
   `cancelled`: nothing was trusted, try again.
4. On done, the SDK requests the secrets by itself
   (`maybeRequestSSSSSecrets`).
5. **Amends the spec:** if the key backup key arrives within a short wait,
   the panel continues into **restoring** with the count, as the recovery key
   route does. If it does not, the panel ends at done.

**Recovery key or passphrase.** `unlock` checks it. On success this device
signs itself and the panel goes to restoring.

- **A partial identity.** If `getCryptoIdentityState()` says cross-signing
  or key backup is missing, `restoreCryptoIdentity` would throw. Instead the
  same key heals it with `initCryptoIdentity(reuseExistingStorageRecoveryKeyOrPassphrase: key)`,
  which never wipes and never makes a new key.
- **Wrong and unreachable are different answers.** A key that opens nothing
  is "that key unlocks nothing". A server that did not answer is "couldn't
  reach loaf.moe · try again". `VerifyState` gains `failed` beside
  `rejected`.

**Restoring.** Counted in sessions against the backup's total, and it carries
on if the panel closes (`worksUnseen`, as now). It does not resume after a
quit, and does not need to: the SDK fetches any missing key from backup when a
room needs it (`maybeAutoRequest` tries online backup first). If the restore
fails part way, the device is already trusted, so the panel finishes with
"restored 1,204 of 3,380 · the rest arrive as you open rooms".

**Setting up recovery.** "Create key" runs `createIdentity(wipe: false)`
with the button busy. If the server asks for authentication (MSC3967 may
exempt the first upload; tuwunel's support is unknown), the panel shows the
same auth step reset uses, then the key.

- **Amends the spec:** by the time the key shows, the identity exists.
  Closing the panel must not lose it. The controller keeps the key for the
  app's run, and the notice reopens on the same key until "I've saved it".

**Resetting identity.** Confirm, then `createIdentity(wipe: true)`. When
`onUiaRequest` asks for authentication, the panel shows the auth step:

- **Password:** the existing field. A wrong password is the existing
  rejection.
- **SSO:** the server's fallback page
  (`/_matrix/client/v3/auth/m.login.sso/fallback/web?session=…`), not the
  sign-in redirect: it hands nothing back to the app. **Amends the spec and
  the roadmap's `ssoInBrowser` note:** on every platform it opens in the
  real browser, and the panel says "finish in your browser" with **I've
  finished**, open it again, and cancel. "I've finished" retries the upload;
  if the server still wants authentication, the panel says so and stays. The
  system sign-in window cannot be used, because nothing would ever close it.

Then the new key shows, as in setting up.

**Incoming "is this you?".** Yes calls `acceptVerification()`, then the same
emoji steps. "That's not me" calls `rejectVerification()`. Closing the panel
lets the request time out. If this device must sign the other but its
self-signing key is not cached (`askSSSS`), the panel asks for the recovery
key inline instead of failing.

## Encrypted rooms

**Writable.** `MatrixTimeline.writable` is `!room.encrypted || trust ==
verified`. Trust comes from one helper shared with `MatrixSession`, so the
two never disagree. **Corrected after the final review:** `MatrixTimeline`
does not notify when trust flips. What carries the flip is the shell: it
rebuilds on the session changing, and the open room's channel view is
rebuilt with the new trust, so its composer appears the moment verification
finishes.

**In place of the composer** (`channel_view.dart` `_EncryptedNote`):

| Trust | Line | Action |
|---|---|---|
| unverified | verify this device to send here | verify: opens the verify panel |
| no identity | set up recovery to send here | set up: opens the setup panel |

The channel view reaches the shell's `_openVerification` through a callback.

**Locked rows** re-map on their own: the SDK re-decrypts on new session keys,
and `onUpdate` already drives a remap. `Message` gains why it is locked:

| Why | Line |
|---|---|
| this device is not verified | encrypted · readable once this device is verified |
| verified, but no key reached this device | encrypted · the key for this never reached this device |

A locked row still offers nothing.

**Actions.** Reply, react, edit and delete work in encrypted rooms wherever
the room is writable; the SDK encrypts relations in `sendEvent`. Phase 3's
"decrypted rows offer only Copy" now follows `writable`.

**Room list previews** of encrypted rooms come from the SDK's last event.
Rehearsal checks they update after a restore; if not, `matrix_rooms.dart`
remaps on it.

## Failure and lifecycle

- Emoji: a mismatch, a cancel from the other side, a timeout or a network
  error all end in `cancelled`.
- Set up or reset failing before the upload changed nothing: try again.
  Reset retries from scratch, which is safe because it wipes anyway.
- Set up or reset failing *after* the new master key went up left an
  identity with no recovery key: the panel lands on reset and says so
  (`IdentityIncomplete`), since only another reset makes a key.
- Signing out or quitting mid-flow disposes the verifier and any
  `KeyVerification` in flight; the other device's request times out.

## Testing

- **Controller** over a fake `Verifier`: every step and transition, and the
  new ones (emoji into restoring, `failed`, the kept setup key, SSO "I've
  finished", `needsKey`).
- **`MatrixVerifier`** over `FakeMatrixApi`: unlock, heal, restore counting
  from served `room_keys`, `initCryptoIdentity` through a UIA round trip, and
  SAS between two in-process clients as the SDK's own tests do. Rehearsal
  probes each first; what `FakeMatrixApi` cannot fake gets a `MockClient`,
  noted under "Found while rehearsing".
- **Widgets:** the composer's replacement line and its action, the locked
  rows' reasons, and `writable` flipping live in an open room.
- **Review Focus**, each with a test: an SDK cancel mid-emoji; the backup key
  arriving after the panel closed; trust flipping with a channel open; a
  relaunch after verifying (trust persists, the composer shows); signing out
  during a restore.
- Existing tests change only where they construct `VerificationController`
  or implement `LoafSession`; the plan names each.

## The live run

In order, each with Chris's okay at the time:

1. Read Chris's identity state (read-only), which settles the partial
   identity branch.
2. Emoji against Element on Chris's account.
3. The recovery key on a fresh sign-in of Chris's account. Chris types the
   key.
4. Set up recovery, then reset, on `@loaf-test:loaf.moe` with a password.
5. The incoming "is this you?": sign in to the test account from Element,
   and loaf vouches for it.

Reset's SSO re-authentication is tested offline only.

## Found while rehearsing

- **The app took part in no verification at all.** `Client.verificationMethods`
  defaults to empty, and the SDK then drops every verification event without
  a word (`KeyVerificationManager.handleToDeviceEvent` returns early).
  `openClient` now declares emoji.
- **Requests to your own devices go out olm-encrypted** as to-device
  `m.room.encrypted`, so a test cannot read their transaction id; the mapping
  of a verification's states is tested in-room, between two users, and the
  own-device request only for going out and being withdrawn.
- **vodozemac loads under `flutter test`** from the macOS build's
  `libflutter_vodozemac.dylib`. Encryption tests need
  `flutter build macos --debug` (or a `flutter run -d macos`) once first,
  and fail saying so without it.
- **`FakeMatrixApi.firstWhere` only sees calls already made**; its stream never
  fires for later ones. The harness polls instead.
- **A reset cancelled at the password or SSO check changes nothing:** the old
  recovery key still unlocks everything afterwards (tested).
- **`restoreCryptoIdentity` needs both halves** of an identity. Cross-signing
  without key backup is healed by the same key; secret storage holding no
  cross-signing keys cannot sign this device, and says the key unlocks
  nothing.
- **Found by the task reviews, all fixed test first:**
  - A cancel sent once a re-auth answer was in flight let the key upload
    land anyway: the identity was replaced and its new keys lost, while the
    app said nothing changed. A challenge now acts only while the server is
    waiting for the person; after that the step can't be stopped.
  - On a real server trust flips to verified as soon as a new identity
    exists, so the notice vanishes and a panel put away on the new key lost
    it for good (the mock flips trust only on "i've saved it"). The panel
    now can't be put away while an identity is being made or its key is
    unsaved (`mustStay`, `PopScope`); on a phone its sheet has no
    drag-to-close, since the sheet's drag pops past `PopScope`.
  - `createIdentity` takes the `wipe` flag after all: setting up
    (`wipe: false`) refuses an account that already keeps secret storage,
    cross-signing (a published master key counts) or a key backup on the
    server, and the panel says so and
    offers reset. A reset (`wipe: true`) replaces them.
  - A mistyped key is a wrong key, never "couldn't reach the server": only
    transport failures read as unreachable.
  - Healing cross-signing without key backup only signs this device when
    the server already holds a backup whose key isn't in secret storage; it
    adds a backup only when the server has none.
  - Back is not offered while a key is being checked or a reset starts.
- **Locked rows re-map live**, proven with a real sealed message whose key
  arrives later: the SDK's timeline retries on `onSessionKeyReceived`. The key
  must reach back to the message's index; an outbound session's own key,
  taken after it encrypted, does not.
- **Why a row is locked is read from `writable`,** not a new `Message` field:
  locked rows exist only in encrypted rooms, where writable means verified.
- **The channel view listens to its timeline** when choosing between the
  composer and the line in its place, but that listening does not carry a
  trust flip: `MatrixTimeline` doesn't notify on one. The shell's rebuild on
  the session changing does (corrected after the final review; an earlier
  line here said the choice followed trust without the shell rebuilding).
- **Room lists show no message previews,** so a restore has nothing there to
  update.
- **Found by reviewing the rehearsal, both hidden by the mock:** saying yes
  to an incoming request left "yes, verify it" live while the real SDK waits
  for the new device to start, so a second tap sent a second answer; it now
  moves to "waiting for the new sign-in to start". And a second request
  arriving while the first's panel was open replaced it, leaving that panel
  on a disposed request; now one is answered at a time. A later one that
  arrives while the first is being answered is dropped, never shown, and
  times out on the device that asked.
- **A request from another of your devices is surfaced whether or not this
  device is verified**: an unverified one being asked is Element's "verify
  this device" from the other side, and answering it verifies both.
- **Found by the final review, both fixed test first:**
  - An incoming "is this you?" ended whatever verify flow was open: the
    shell disposed it to make room, so a panel making a key, or showing one
    unsaved, froze and the key was lost; history restoring unseen stopped.
    Incoming requests now have their own flow, made and ended with their
    panel, stacked over any open one; a flow that works unseen is reopened,
    never replaced.
  - A set-up or reset that failed after the new master key went up (backing
    up keys, storing secrets) said "nothing changed · try again", though the
    old identity was gone and the new one had no recovery key.
    `createIdentity` now compares the published master key before and after
    and throws `IdentityIncomplete`; the panel lands on reset and says "your
    new identity went up but didn't finish, so it has no recovery key yet ·
    reset again to get one".
  - Also from that review: setting up refuses an account whose master key
    is published even with nothing in secret storage; restoring ends at once
    on an account with no key backup; vouching reads a mistyped key as wrong,
    through the same mapping as unlocking; each emoji answer is sent once.
- **Saving the key:** a share sheet that reports "unavailable" counts as not
  saved. The macOS sandbox needs `com.apple.security.files.user-selected.read-write`
  for the save panel.
- **After a new identity, the fake server keeps serving the old device
  signatures,** so tests see this device's new one only as uploaded.
